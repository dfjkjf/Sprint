# Week 3：网络协议与 RTPS

Week2 从 ROS 2 的视角看了消息怎么走；这一周沉到线协议，看 DDS 到底在网络上发了什么、怎么保证可靠、发现要花多少时间、QoS 每一项在协议里对应哪段行为。

边界：Week2 的 QoS 讲的是 ROS 2 接口能配什么、映射到哪；这一周讲 DDS 自身的语义与实现代价。共享内存的结构在 Week2 已经讲过，这里只讲它作为传输通道的取舍。

Day 1 传输与网络基础，Day 2 RTPS 协议机制，Day 3 发现，Day 4 QoS 语义与调优。

## Day 1｜传输与网络基础

### Q1 TCP 和 UDP 的差异是什么？为什么 DDS 默认用 UDP？

TCP 提供可靠、有序的字节流，有连接、有拥塞控制、有重传；UDP 是无连接的数据报，不保证送达、不保证顺序，但开销小、支持组播。

DDS 默认选择 UDP，有三个原因。第一是延迟：TCP 的三次握手、拥塞控制和确认机制都会引入额外的往返，而实时控制更在意单次传输的时间而不是平均带宽。第二是组播：发现和小规模数据分发需要组播来避免 N 方两两建立连接，TCP 根本不支持组播。第三是队头阻塞：TCP 一旦丢包，后面的数据即使已经到达也必须等待重传，而 DDS 可以只重传丢失的那一段。

代价是可靠性要由 DDS 自己在应用层实现——这正是 RTPS 里 HEARTBEAT 和 ACKNACK 存在的原因。在跨 NAT、穿防火墙、或者链路质量很差的场景下，仍然可以在 DDS 上配置 TCP 传输，但那属于特例。

### Q2 UDP 不可靠，DDS 是怎么在它之上做可靠传输的？

三件事配合：序号、心跳、确认。

每个样本有单调递增的序号。发送方周期性发送 HEARTBEAT，告知接收方"我这里已经产生了到某个序号的数据"。接收方比对本地已收到的序号，把缺口通过 ACKNACK 报回去。发送方收到 ACKNACK 后，把缺失的样本重新投递。

这套机制的代价是延迟下限被拉长：一次可靠投递至少需要一个心跳周期才能发现丢包。所以心跳周期是可调参数——调小则恢复快但带宽和 CPU 开销大，调大则恢复慢。在低延迟场景里，通常会针对关键 topic 单独调小心跳间隔。

另外，可靠性是有前提的：如果发送方的 History 已经把这个样本挤出去（`KEEP_LAST` 深度不够），重传也拿不到数据，接收方最终会收到 Gap 消息，表示这段序号永久缺失。

### Q3 分片发生在哪一层？为什么要避免依赖 IP 分片？

存在两种分片：网络层的 IP 分片，和 RTPS 协议自己的分片机制。

IP 分片的问题在于：任何一片丢失，整个原始数据报都要重传，因为 IP 层没有部分重传的能力。而且很多防火墙和 NAT 设备对分片包的处理不一致，甚至会直接丢弃。所以 RTPS 推荐自己分片——把大样本切成多个 RTPS 子消息，每个子消息是一个独立的 UDP 包，丢失时可以只重传缺失的那几片。

以太网 MTU 通常是 1500 字节，扣掉 IP 头和 UDP 头后有效载荷约 1472 字节。所以一条 6MB 的消息要切成几千片，这个数量级直接决定了丢包时的重传成本。

这也解释了一个现象：大消息在丢包环境下的延迟抖动远大于小消息，因为恢复粒度不一样。

### Q4 组播为什么对发现很重要？有什么坑？

组播让一个发送方一次就能触达所有接收方，发现阶段因此不用做 N 方两两握手。DDS 的 SPDP 默认就是用固定的组播地址和端口周期性宣告自己的存在。

坑有四个。交换机默认可能不开启 IGMP snooping，导致组播被当作广播泛洪到所有端口，在大型网络里直接打满链路。无线网络对组播的支持很差，通常降级为最低速率发送，丢包率高。云环境和容器网络往往不支持组播，跨主机发现直接失效。容器内多网卡时，组播要绑定到正确的那张网卡，否则宣告从错误的接口出去。

所以在跨主机、容器化、或者无线场景里，通常要改用单播发现（初始对等列表）或集中式发现服务，而不是依赖组播。

### Q5 为什么 UDP 传输无法做到真正的零拷贝？

因为数据必须经过内核的 socket 发送缓冲区和接收缓冲区，这一层是内核管理的，用户态无法绕过。

`send` 的实际路径是：用户缓冲区拷贝到内核 socket 缓冲区，网卡驱动再从内核缓冲区取走交给硬件（中间可能有 DMA，但用户态到内核态那一次拷贝省不掉）。接收侧同理，数据先进入内核缓冲区，再拷贝到用户缓冲区。

有一些优化手段能减少拷贝次数：`sendmmsg` 批量发送降低系统调用次数，`MSG_ZEROCOPY` 让内核直接引用用户页（但受限于页对齐和完成通知机制，实际收益有争议），以及 XDP/AF_XDP 这类绕过协议栈的方案。

真正的零拷贝只在共享内存路径上成立——两个进程映射同一块物理页，内核完全不参与数据搬运。这也是为什么同机通信要用共享内存而不是环回网络。

### Q6 环回（loopback）通信有什么特点？能和共享内存比吗？

环回走的是内核网络栈：数据从发送方的内核 socket 缓冲区直接送到接收方的内核 socket 缓冲区，不经过网卡。相比物理网络它省掉了硬件延迟和驱动处理，但仍然有系统调用、内核协议栈处理、以及两次拷贝。

实测中环回的延迟通常在几十微秒量级，而共享内存可以做到微秒级甚至更低，差距主要来自协议栈路径。带宽差距更大，环回受限于单核的协议栈处理能力。

所以同机跨进程通信，共享内存是有实质收益的；跨机才必须走网络。判断依据不是"能不能通"，而是"这段延迟在总预算里占多少"——如果回调本身耗时几毫秒，环回省下的几十微秒就不值得为它引入共享内存的复杂度。

## Day 2｜RTPS 协议

### Q7 RTPS 和 DDS 是什么关系？

DDS 是一个规范，定义了两部分：应用层 API 与 QoS 语义（DCPS 层），以及互操作协议（RTPS 层）。

RTPS 全称 Real-Time Publish-Subscribe，是 DDS 的线协议标准。它规定了报文格式、实体发现流程、可靠性机制、分片方式，目的是让不同厂商的实现能够互通。

关系可以这样表述：DDS 是"接口和数据模型的规范"，RTPS 是"在网络上怎么表达这些语义的规范"。厂商实现通常同时提供两者，比如 Fast DDS 和 Cyclone DDS 都实现 DDS API 并通过 RTPS 互通。

理解这个分层的价值在于：跨厂家互通问题一定出在 RTPS 层而不是 API 层，因为 API 各自独立实现，只有线协议是共享的契约。

### Q8 RTPS 的实体模型是怎样的？

分成两组实体。

DDS 层的实体是业务可见的：DomainParticipant、Publisher、DataWriter、Subscriber、DataReader。它们规定了谁发布、谁订阅、有什么 QoS。

RTPS 层的实体是协议内部的：RTPSParticipant、RTPSWriter、RTPSReader，以及 Change（一个待传输的数据变更）。Writer 和 Reader 之间通过匹配（match）建立关联，匹配的依据是 topic 名、类型名和 QoS 兼容性。

一个 DataWriter 通常对应一个 RTPSWriter，但内部维护的是 Change 队列。每个 Change 携带序号（seq num）和源时间戳，这两个字段是后续所有可靠性机制的基础。

调试时区分这两层很重要：`ros2 topic info` 看到的是 DDS 层实体，抓包看到的是 RTPS 子消息，两者之间隔着一层映射。

### Q9 WriterHistory 和 ReaderHistory 各自的作用是什么？

WriterHistory 保存已发送但尚未被所有读者确认的样本，是重传的数据来源；ReaderHistory 保存已接收但尚未被应用取走的样本，是应用消费的缓冲。

WriterHistory 的深度由 QoS 的 History 策略决定。`KEEP_LAST(n)` 只保留最近 n 个，超出后最旧的被丢弃——这时的后果是不可恢复的：读者若还没收到被丢弃的样本，重传也拿不到，只能收到 Gap。`KEEP_ALL` 保留全部未确认样本，代价是内存随积压线性增长，极端情况下会耗尽资源。

ReaderHistory 同理，如果应用取数据太慢，`KEEP_LAST` 会让旧样本被新样本覆盖，表现为"丢数据但没有任何错误报告"。

这两个队列是 DDS 内存问题的第一现场：排查内存持续增长时，先看这两处的样本数和水位，比看进程堆更直接。

### Q10 HEARTBEAT 和 ACKNACK 是怎么工作的？

两者的配合构成可靠传输的闭环。

Writer 周期性发送 HEARTBEAT，内容是一个序号区间（firstSN 到 lastSN），表示"我这边的数据已经产生到这个位置"。这个区间允许读者判断自己是否落后。

Reader 收到后对比本地状态：已经连续收到的部分不需要处理，中间的空洞通过 ACKNACK 的位图报回给 Writer，同时告知自己当前的可用状态。

Writer 收到 ACKNACK 后，把这些序号对应的样本重新投递（从 WriterHistory 中取）。如果某个序号已经被 History 丢弃，Writer 会发送 Gap 子消息，告诉读者这段永久不可用，避免读者一直等待。

关键参数是心跳周期和 NACK 响应延迟。前者决定发现丢包的速度，后者决定重传的触发时机。低延迟配置通常把心跳周期压到几十毫秒，重传几乎即时触发；默认配置可能到秒级，适合带宽受限的场景。

### Q11 可靠传输的重传为什么会造成延迟尖峰？

因为重传是"事后发现"，天然带有至少一个心跳周期的滞后。

链路丢了一个包，接收方要等下一次 HEARTBEAT 到达并比对后才知道缺了什么，然后发 ACKNACK，发送方再重传。这三步串起来，最短恢复时间约为心跳周期的 1.5 到 2 倍。

更麻烦的是重传本身会加剧拥塞：如果丢包是拥塞引起的，重传会进一步加大负载，形成正反馈，表现为延迟从几十毫秒突然跳到几百毫秒。UDP 上 DDS 有自己的流控参数（发送窗口、每读者的发送配额），但没有 TCP 那样成熟的拥塞控制。

缓解手段有三个：把心跳周期和 NACK 延迟调到与业务实时性匹配的数量级；给关键 topic 用独立的 participant 和线程，避免和非关键流量争抢；以及从源头控制单次爆发量，避免一次写入大量样本把链路打满。

### Q12 Gap 消息是干什么的？

Gap 是 Writer 发给 Reader 的"跳过声明"，表示某个序号区间的数据不会再提供了。

产生 Gap 有两种情况。一是样本被 WriterHistory 挤掉了（`KEEP_LAST` 深度不足），真数据已经不存在。二是某些序号本来就不会产生数据，比如样本在写入后被内容过滤掉。

Gap 的作用是解除读者的等待。如果没有 Gap，读者会一直认为这些序号"还没到"，保留在待接收状态，既占内存又让 ACKNACK 一直重复报告同一个缺口，形成无效重传循环。

排查丢数据时，Gap 是一个关键信号：出现 Gap 说明数据在发送端就已经丢了（History 覆盖或过滤），而不是网络问题。这个区分能直接把排查方向从网络转到 QoS 配置上。

### Q13 Deadline 和 Liveliness 分别解决什么问题？

Deadline 描述的是"数据更新频率的承诺"：Writer 承诺在 deadline 周期内至少发布一次，Reader 如果在两个周期内没有收到新样本，会触发 deadline missed 回调。它的用途是检测数据源失效，而不是检测网络故障。

Liveliness 描述的是"实体还活着的承诺"，粒度可以是 participant 级或 writer 级，检查方式可以是按周期自动发送心跳，也可以由应用主动声明（`assert_liveliness`）。超时后读者会认为该 writer 已失效，触发 liveliness changed 回调。

两者常被混用，区别在于 Deadline 关注"数据是否持续更新"，Liveliness 关注"发布者是否还存在"。一个周期性发送但内容不变的传感器，Liveliness 正常但可能违反 Deadline；一个进程崩溃的发布者，两者都会触发。

实现上，Liveliness 需要额外的保活流量，在节点数量多的系统里这部分开销不可忽略。

### Q14 XCDR1 和 XCDR2 有什么区别？

两者都是 CDR（Common Data Representation）系列的序列化格式，规定了基本类型的字节序、对齐和结构排布方式。

XCDR1 是较早的版本，成员按声明顺序紧排并做对齐，不支持可选的成员缺席，所以类型一旦演进（加字段），两端的布局就会不一致，兼容性依赖额外规则。

XCDR2 引入了可变长编码（成员带长度前缀或 EMHEADER），支持成员可选、支持更灵活的类型演进，也更适合大消息和稀疏结构。代价是编码解码的 CPU 开销略高。

选择上，互通场景要按对方的支持能力来定；纯内部通信且类型会演进，优先 XCDR2。需要注意的是，序列化格式不匹配时往往不会报错，而是表现为收到乱码或字段错位，排查时先确认两端的类型定义和编码版本是否一致。

### Q15 类型兼容性（XTypes）是怎么判定的？

XTypes 定义了类型系统与兼容性规则，核心是把兼容性分成两个层次：类型等价（equivalence）和类型可赋值（assignability）。

等价的含义是类型结构完全一致，可以互相理解。可赋值的含义是允许通过规则化的演进——比如在末尾追加可选字段、放宽取值范围——仍然能被正确解析。

运行时通过 TypeObject 交换类型信息，发现阶段就能判断两端的类型是否兼容，不兼容则不会匹配。这是比"收到数据才发现字段对不上"更早的失败方式。

实际工程里最容易出问题的是：两端用了同一份 IDL 但分别编译，字段顺序或默认值不同；或者一端使用了动态类型而另一端是静态类型——两者在线上格式上必须完全对齐，否则互通会静默失败。

## Day 3｜发现机制

### Q16 SPDP 和 SEDP 分别做什么？

发现分两步，对应两个内建协议。

SPDP（Simple Participant Discovery Protocol）负责"发现有哪些参与者"。每个 DomainParticipant 启动后，周期性向固定的组播地址和端口发送宣告，内容包含参与者的标识、租约时长、以及用于后续单播通信的 locator。收到宣告的一方会记录这个参与者，并在租约到期前持续刷新。

SEDP（Simple Endpoint Discovery Protocol）负责"这个参与者里有哪些读写者"。参与者之间建立单播连接后，通过内建的可靠 writer/reader 交换各自的 endpoint 信息，包括 topic 名、类型名、QoS 配置。

两步的分工决定了故障现象：SPDP 不通表现为"完全看不到对方"，SEDP 不通表现为"能看到对方但看不到 topic"。

租约机制（lease duration）也是排查重点：宣告周期必须明显小于租约时长，否则会出现参与者反复上下线。

### Q17 一次完整的发现大概要多久？时间花在哪？

默认配置下，从进程启动到两端能收发数据，通常在几百毫秒到几秒之间。

时间主要花在三处。SPDP 的宣告周期，默认可能是几百毫秒到数秒，如果启动时刻刚好错过一个周期，就要等下一轮。SEDP 的交换要等 SPDP 匹配完成后才开始，又是一次往返。最后是端点匹配和 QoS 兼容性检查。

对启动时序敏感的系统，这三段延迟会直接体现在"第一个控制周期来得太晚"上。所以常见做法是：调小 SPDP 宣告周期和初始宣告次数（Fast DDS 有 initial announcements 参数），或者改用集中式发现，让新节点主动向已知的发现服务注册，避免等待组播周期。

测量方法可以直接抓包数时间戳，也可以用 ros2_tracing 的 discovery 相关 tracepoint，比读文档估算可靠。

### Q18 什么是集中式发现（Discovery Server）？为什么大系统需要它？

集中式发现把组播宣告换成"所有节点向一个（或少数几个）发现服务注册"，由服务把匹配结果转发给相关节点。

需要它的原因是发现流量随节点数呈平方增长。N 个节点各自周期宣告，总量是 O(N²) 级别的报文——几十个节点时还能接受，上百个节点时会占满带宽和 CPU，而且每个节点都维护着所有其他节点的状态，内存也随之膨胀。

集中式把复杂度降到 O(N)：每个节点只与服务通信，服务负责匹配。代价是引入单点依赖——发现服务不可用会阻断所有新的匹配，所以生产环境通常做主备或者冗余部署。

这也是车载和机器人域控从"纯组播发现"走向"发现服务 + 域隔离"的根本原因，属于规模化之后的必然选择。

### Q19 发现流量过大会造成什么后果？

三类后果，且往往同时出现。

带宽上，周期性的宣告和保持心跳会占用固定比例的链路容量，在百兆网络上这个比例可能到百分之几，直接影响业务数据的可用带宽。

CPU 上，每个节点都要解析收到的所有宣告、维护远端参与者状态、周期性检查租约是否过期。节点数多了之后，这部分开销不再可以忽略，表现为系统空闲时 CPU 也降不下来。

内存上，每个远端 participant 和 endpoint 都对应一份内部对象，加上 SEDP 交换的类型信息（TypeObject 可能很大），内存占用会随节点数增长。这类增长是"跟着拓扑涨"而不是"跟着业务数据涨"，容易被误判为内存泄漏。

缓解手段是域隔离（把不相关的节点放进不同 domain）、分区（partition 做逻辑隔离）、集中式发现、以及按需延长宣告周期。

### Q20 Domain 和 Partition 怎么隔离？两者有什么区别？

Domain 是硬隔离：不同的 domain ID 使用不同的端口区间（默认基准端口加上 ID 的倍数偏移），发现和通信完全独立，互不可见。跨 domain 的节点永远不会匹配。

Partition 是软隔离：在同一个 domain 内，通过名字（可以是多级、支持通配符）对 endpoint 做逻辑分组，只有名字匹配的读写者才会建立关联。发现流量仍然共享同一个 domain，但不会产生跨 partition 的数据投递。

选择的依据：如果两组业务完全无关、且希望连发现开销都分开，用 domain；如果是同一系统内的模块划分，只是想避免订阅到不该收的数据，用 partition。

实际使用中的坑是：domain ID 太多会占用大量端口，某些系统对端口区间有限制；partition 的通配符匹配规则各实现略有差异，跨厂家互通时要用最保守的写法（完全相同的名字）。

## Day 4｜QoS 语义与调优

### Q21 Reliability 和 History 的组合会带来什么差异？

这两个 QoS 是耦合的，单独调其中一个通常得不到预期效果。

`RELIABLE` 配合 `KEEP_ALL`：保证不丢，但积压会一直占内存，恢复能力取决于内存上限，积压到顶后写入会阻塞或失败。

`RELIABLE` 配合 `KEEP_LAST(n)`：允许在积压时丢弃最旧的未确认样本，之后的缺口通过 Gap 告知读者。这是"保证尽力而为"而不是"保证不丢"——很多人误以为 RELIABLE 就等于不丢，实际上深度不够时照样丢。

`BEST_EFFORT` 配合任意 History：不重传，History 只影响读者侧能取到多少历史样本。

所以正确的问法不是"要不要可靠传输"，而是"在多大的缓冲预算下保证可靠"。深度 n 的实际含义是：允许最多 n 个样本的在途窗口，超出的部分必然丢失。

### Q22 KEEP_LAST 和 KEEP_ALL 在实际行为上有什么差别？

`KEEP_LAST(n)` 是固定容量环形语义：新样本进来，超过 n 个就覆盖最旧的，不区分对方是否已经收到。它的内存占用有确定上界，行为可预测。

`KEEP_ALL` 是保留全部未确认样本：只要还有读者没确认，就不能删。内存占用取决于最慢的那个读者——一个卡住的读者会让整个 writer 的队列无限增长。

这就解释了生产环境里最常见的两类故障：用 `KEEP_ALL` 的系统在某个订阅者异常后内存持续上涨，最终 OOM；用 `KEEP_LAST` 的小深度的系统在短时抖动后出现数据空洞，而且因为发了 Gap，不会有任何错误日志。

选择原则很直接：传感器这类"只要最新值"的数据，深度 1 到几就够；状态事件这类"不能丢"的数据，用 `KEEP_ALL` 但必须配合资源上限（max_samples、max_instances）和监控。

### Q23 TRANSIENT_LOCAL 的持久性是怎么实现的？代价是什么？

`TRANSIENT_LOCAL` 表示 writer 会为"迟到的读者"保留历史样本：新加入的 reader 匹配成功后，writer 会把 History 中仍在的样本补发一遍。

实现上，writer 不能因为样本被所有现有读者确认过就释放，必须额外保留到 History 深度允许的范围。这就是它的代价——内存占用由 History 深度决定，与读者数量和确认状态无关。

常见用途是"配置下发"和"最后状态同步"：后启动的模块需要立刻拿到当前参数或最新状态，不适合用 VOLATILE 让它等下一次更新。

注意它的名字容易误导：`TRANSIENT_LOCAL` 只在 writer 进程存活期间有效，进程重启后历史就没了。要跨重启保留，需要 `TRANSIENT`（依赖外部持久化服务）或 `PERSISTENT`，两者实现复杂度和成本高一个量级。

所以"持久性"这个词在 DDS 里是分级的，面试里被问到要能立刻说清是哪一级。

### Q24 TimeBasedFilter 是做什么的？实现时要注意什么？

它限制 reader 对同一实例的最小接收间隔：间隔内的样本被丢弃，不投递给应用。

关键点是它的作用位置——过滤发生在 reader 侧，数据仍然会通过网络到达并被接收，只是不投递给应用。所以它省的是应用处理开销和下游压力，不省带宽，也不减少 RTPS 流量。这一点经常被误解成"能降网络负载"。

典型场景是降频消费：传感器以 100Hz 发布，某个订阅者只需要 10Hz，就用 TimeBasedFilter 设为 100ms，而不需要发布端提供两套频率。

实现上有两个必须明确的选择。一是时间源的选取：用样本携带的源时间戳，还是用本地接收时间。用源时间戳时，如果两端时钟不同步，过滤行为会与预期偏离；跨时钟域或者时间戳不单调的情况下，可能出现该滤的没滤、不该滤的被滤。用接收时间则依赖本地单调时钟，行为更可预测，但会受网络抖动影响。二是与 History 的交互：被过滤掉的样本是否仍占用 reader 的 History 槽位，各实现的行为不完全一致，需要实测确认，否则可能出现"过滤后反而更容易丢数据"的意外结果。

### Q25 QoS 不匹配导致的故障怎么排查？

典型的故障现象是"topic 能看到，数据收不到，也没有任何报错"。这几乎总是 QoS 兼容性问题。

排查顺序：先用 `ros2 topic info --verbose` 把双方的 QoS 逐项列出来对比，重点看 Reliability、Durability、History 深度这三项。再看 `ros2 topic hz`，如果发布端有频率而订阅端没有，说明匹配失败；两端都正常但应用收不到，问题在回调或 executor 侧。

如果用的是原生 DDS 而不是 ROS 2，对应手段是查看内建 topic 的状态（`DCPSPublication`、`DCPSSubscription`），或者打开实现的日志看匹配过程。

还有一类不是"不匹配"而是"行为不符"：QoS 能配上，但深度不足导致高负载下静默丢样本；或者 Deadline 设置过严导致频繁误报。这类只能靠计数指标发现——统计发送数、接收数、Gap 数，三者对不上就说明有丢失。

### Q26 如何用 QoS 把"丢包"和"延迟"两类问题分开解决？

先判断瓶颈类型，再动 QoS，顺序反了会互相抵消。

丢包问题的处理路径：确认是网络丢包还是队列覆盖。抓包看 RTPS 层是否有重传，如果有重传且最终补齐，那是链路质量问题，调小心跳周期、降低单次爆发量；如果没有重传或发了 Gap，那是 History 深度不足，要加深深度或者降低发布频率。同时检查资源上限（max_samples）是否把样本挡在了入口。

延迟问题的处理路径：先分段定位（序列化、传输、接收、executor 排队），再针对性调整。传输段慢通常是心跳/重传配置或带宽饱和；接收侧慢是 History 积压，要加深深度或加快消费；executor 侧慢是回调阻塞，属于 Week1 的线程模型问题。

需要警惕的反向关系是：加深 History 深度能缓解丢包，但会增加延迟和内存；提高 Reliability 能减少丢包，但重传会加剧拥塞时的延迟。所以两个目标不能靠同一组参数同时优化，必须按业务确定哪个是硬约束。
