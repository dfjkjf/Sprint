# Week 2：进程、虚拟内存与 ROS 2 运行时

Week1 讲的是对象怎么分配、线程怎么协作；这一周往下走一层，看这些对象落在什么样的地址空间里，一次缺页、一次映射切换会带来多少延迟，以及 ROS 2 的运行时如何把这些线程组织成一条消息链路。

Day 1 进程与虚拟内存，Day 2 ROS 2 运行时。两者是同一条线：Executor 是线程模型问题，虚拟内存决定了消息 buffer 的真实成本。

## Day 1｜进程与虚拟内存

### Q1 一个进程的虚拟地址空间是怎么布局的？

从低地址到高地址依次是：代码段、已初始化数据段、未初始化数据段（bss）、堆、内存映射区（mmap）、栈，再往上是内核空间。

64 位 Linux 的用户空间通常到 `0x00007fffffffffff`，再往上是内核态保留区；每个进程有独立的页表，进程切换要换页表基址寄存器，同时导致 TLB 失效，这是进程切换比线程切换昂贵的主要原因。

这个布局的实际意义在于：堆上的大对象是私有匿名页，而共享内存段是挂在 mmap 区的文件映射——两者属于不同的内存类型，回收策略、缺页行为、能否被换出都不一样。分析一条 6MB 消息的开销时，要先分清它落在哪一类。

### Q2 页表是什么？为什么需要多级页表？

页表负责把虚拟地址翻译成物理地址，以页为单位，x86-64 上通常是 4KB。

如果只用一级页表，47 位地址空间除以 4KB 得到约 2^35 个页表项，每项 8 字节，合计几百 TB，任何进程都放不下。多级页表把地址切成分段索引，只对实际用到的区域建表，稀疏性是它省内存的根本原因。x86-64 常规是四级（PGD、PUD、PMD、PTE），每级 512 项。

代价是翻译一条地址要访问多级页表，所以 CPU 用 TLB 缓存最近的翻译结果。TLB 命中只需一个周期级开销，TLB miss 则要完整走一遍页表（数次内存访问），这就是大页能提升性能的原因——它用更少的 TLB 项覆盖更大的地址范围。

### Q3 什么是缺页异常？minor fault 和 major fault 有什么区别？

访问的虚拟页当前没有可用的物理页或没有建立映射时，由硬件触发异常，内核接管并补上映射，然后重新执行那条指令。

minor fault 指页已经在物理内存里，只是没有把页表项建起来——典型场景是首次访问匿名页、写时复制（fork 之后写）、或者一块刚分配还没碰过的内存。开销在几微秒量级。

major fault 指页不在内存，需要从磁盘或文件系统读进来——典型场景是 mmap 一个文件后首次访问、或者 swap 换入。开销取决于存储，机械盘可能是几十毫秒，NVMe 也在几十微秒以上。

对通信组件的实际影响：即使内存池预先分配好了缓冲区，第一次写入仍会触发大量 minor fault；如果想让延迟可预测，需要在启动阶段把池子整个碰一遍（预触碰），甚至在实时路径上用 `mlock` 锁住。

### Q4 `mmap` 和 `read`/`write` 有什么区别？为什么说 `mmap` 更快？

`read`/`write` 的路径是：数据先进入内核的 page cache，再从 page cache 拷贝到用户缓冲区，存在一次明确的数据拷贝，并且是一次系统调用。

`mmap` 是把文件的物理页直接映射进用户地址空间，访问时按需缺页，省掉了那次内核到用户的拷贝，也省掉了系统调用本身的固定开销。

但 `mmap` 不是无条件更快。它的成本转移到了缺页异常和页表维护上——首次访问每一页都要触发一次 fault；文件被截断或被回收时访问会触发 SIGBUS；`munmap` 还要做 TLB 刷新。所以小数据、一次性的读写用 `read` 更划算；大文件、反复随机访问、或者多进程共享同一份数据，`mmap` 才有优势。

还有一点常被混淆：`mmap` 省的是用户态与内核态之间的拷贝，数据从磁盘到 page cache 的那一步并没有省掉。

### Q5 共享内存的本质是什么？为什么它能做到零拷贝？

两个进程把同一块物理页同时映射到各自的虚拟地址空间。进程 A 写入后，进程 B 直接读到修改后的内容，整个过程中内核不参与数据搬运——这才是真正意义上的零拷贝。

实现方式有三种：POSIX 共享内存（`/dev/shm` 下的文件加 `mmap`）、System V 共享内存（`shmget`/`shmat`）、以及 `memfd_create`。三者底层都是同一块页被多个页表项指向。

它带来的新问题是同步：内核不再替你解决竞争，生产者和消费者之间必须自己建立信号机制（原子变量、futex、信号量）。通道本身也不提供生命周期管理——一块 chunk 什么时候能被复用，需要引用计数或所有权协议来保证，这正是 iceoryx 这类方案要解决的核心问题。

### Q6 为什么在高频场景下，普通的内存分配代价很高？

glibc 的 `malloc` 有两条路径：小于阈值（默认 128KB，且会动态调整）的分配走 arena 和空闲链表，大于阈值直接 `mmap`。

6MB 的消息每次都落在 `mmap` 路径上，于是每次分配对应一次系统调用、一次 VMA 建立、以及首次写入时的连续缺页；每次释放对应一次 `munmap` 和 TLB 刷新。单次开销量级在微秒到几十微秒，而且随系统状态波动——这就是分配延迟抖动的来源。

内存池的价值正在这里：启动时一次性申请一大片，之后取用和归还都是用户态的空闲链表指针操作，纳秒量级，且没有系统调用，不会触发内核的内存管理路径。

需要注意池化只解决了分配，没有解决首次触碰的缺页——那部分要靠预触碰或 `mlock`。

### Q7 透明大页（THP）对延迟有什么影响？

大页的价值是减少 TLB miss：覆盖 2MB 内存，4KB 页需要 512 个 TLB 项，2MB 页只需要 1 个。

但 THP 是内核自动决策的，会带来两个副作用。一是首次缺页时要分配并清零整块 2MB，形成一次明显的延迟尖峰；二是后台的 `khugepaged` 线程会周期性地扫描和合并页，与业务线程争抢 CPU 和内存带宽，表现为周期性抖动。

对延迟敏感的系统通常显式关闭 THP，改用 `hugetlbfs` 预分配固定的大页——这样既有 TLB 收益，又不会在运行时产生尖峰。折中的做法是对特定区域用 `madvise(MADV_NOHUGEPAGE)`。

判断是否需要大页的方法很直接：用 `perf stat` 看 TLB miss 占比，如果占比很低，关闭 THP 不会有损失。

### Q8 内存回收会怎么影响延迟？

物理内存紧张时，内核要回收页：page cache 可以直接丢弃（干净页）或写回（脏页），匿名页需要换出到 swap，slab 缓存会收缩。

分两条路径：后台的 `kswapd` 按水位（min/low/high）逐步回收，影响相对平滑；当分配时发现水位已低于 min，会同步执行直接回收（direct reclaim），这条路径发生在调用者的上下文里，可以让一次 `malloc` 或一次缺页停顿几毫秒到几十毫秒。

对实时系统，这意味着即使代码里没有任何阻塞调用，延迟也可能突然变大。缓解手段是调高 `min_free_kbytes`、调整 `watermark_scale_factor` 让后台回收更早介入、把关键缓冲区 `mlock` 住不被回收、以及避免在实时路径上产生大量 page cache（比如日志写文件）。

### Q9 swap 对实时系统意味着什么？

swap 把不常访问的匿名页换出到磁盘，回收物理内存。问题在于换入的时机不可控：一次访问命中被换出的页，就会触发 major fault，延迟从微秒级跳到毫秒级甚至更高，而且这条路径通常会持有内存管理相关的锁，连带影响其他线程。

对延迟敏感的场景，常规做法是完全关闭 swap，或者保留极少量的 swap 仅作为 OOM 前的缓冲，同时调低 `vm.swappiness`。

比 swap 更隐蔽的是内存超卖：`overcommit` 允许进程申请超过物理内存的虚拟空间，真正分配发生在触碰时，一旦触碰时没有可用内存，进程会被 OOM killer 直接终止。所以容量规划要按实际驻留量（RSS）而不是虚拟大小来做。

### Q10 怎么观测一个进程的内存行为？

从粗到细分四层。

`/proc/PID/status` 看四个总量：VmSize（虚拟大小）、VmRSS（实际驻留）、VmSwap（换出量）、RssAnon 与 RssFile（匿名页和文件页的拆分）。判断是否泄漏主要看 VmRSS 是否单调上涨。

`/proc/PID/smaps` 按 VMA 列出每一段的 RSS、PSS、共享与私有比例，能定位到是堆在涨还是共享内存在涨。

`perf stat -e page-faults,minor-faults,major-faults` 统计缺页次数，minor 多说明首次触碰频繁，major 多说明内存不足或在访问磁盘。

`mincore()` 可以查询指定地址范围里哪些页当前驻留在内存，适合验证"我以为预热过了"这类假设。

判断泄漏与积压的分界始终是那三条：是否单调增长、是否可回收、增长是否与业务负载对应。

### Q11 page cache 与 DDS 大消息有什么关系？

普通 DDS 传输走的是 socket，数据从用户缓冲区进入内核 socket 缓冲区，不经过 page cache。所以纯网络传输路径上，page cache 不是主要因素。

会引入 page cache 的有三类场景：一是录包和回放（写文件），`write` 返回只代表数据进了 page cache，不代表已落盘；在实时路径上调用 `fsync` 会造成不可控的阻塞。二是加载大文件（地图、模型）后做 mmap，后续访问时如果这段页被回收，会触发 major fault。三是容器环境下，page cache 计入 cgroup 的内存用量，可能触发 cgroup 级别的回收，表现出来的现象是"进程自己没分配，延迟却变大了"。

结论：分析通信延迟时不要只看进程自身的堆，还要看它间接产生的文件 IO 和共享映射。

## Day 2｜ROS 2 运行时

### Q12 rclcpp、rcl、rmw 三层各管什么？

`rclcpp` 是 C++ 用户接口层，提供 Node、Publisher、Subscription、Executor、参数、时间、回调组这些概念，是业务代码直接面对的层。

`rcl` 是用 C 实现的公共层，负责 ROS 图的管理、名字解析与重映射、参数服务、QoS 结构体的规范化，向上对 rclcpp 和 rclpy 提供同一套语义。

`rmw` 是中间件抽象接口，定义 publisher、subscription、take、wait、QoS 转换这些操作，具体实现有 `rmw_fastrtps_cpp`、`rmw_cyclonedds_cpp` 等。

分层的收益是上层代码不依赖具体 DDS 实现，换实现只需换 `RMW_IMPLEMENTATION` 环境变量。代价是每一层都有间接调用和类型擦除，排查问题时必须能判断问题出在哪一层：回调不并发是 rclcpp 回调组的问题，topic 名字对不上是 rcl 名字解析的问题，收不到数据往往是 rmw 层 QoS 转换或 DDS 发现的问题。

### Q13 RMW 抽象的意义是什么？不同实现之间的差异体现在哪？

意义是让 ROS 2 能同时支持多个 DDS 实现，并允许非 DDS 的中间件接入。协议栈的能力差异被收敛到一组能力查询接口里。

差异主要体现在四处。默认 QoS 细节不同，比如历史深度和资源限制的默认值。发现机制的具体实现不同，SPDP/SEDP 的报文节奏和默认端口有差异。共享内存方案不同，Fast DDS 自带 SHM transport，而 Cyclone DDS 走 iceoryx。线程模型不同，参与者、接收、事件线程的数量和优先级策略不一。

所以"换个 RMW 性能就变了"是正常现象，做性能对比时必须声明用的是哪个实现和哪个版本，否则数据不可比。

### Q14 一条消息从 publish 到 callback 经历了什么？

发送侧：`rclcpp::Publisher::publish` 经过 `rcl_publish` 到 `rmw_publish`，再进入 DDS 的 `DataWriter::write`。此时发生序列化，把结构化消息压成连续字节；结果写入 writer 的 HistoryCache；RTPSWriter 组包后交给 Transport，走 UDP 或共享内存。

接收侧：DDS 的接收线程从 Transport 收包，重组为样本放入 reader 的 HistoryCache，然后通过 wait set 通知上层有数据可取。

用户侧：executor 线程在 `rmw_wait` 上被唤醒，取到 ready 的 subscription，执行 `rmw_take` 把数据取到用户缓冲区（这一步可能触发反序列化），最后调用用户回调。

延迟由五段构成：序列化、发送排队、传输、接收重组、executor 唤醒与回调执行。定位延迟问题时要先判断超时发生在哪一段，而不是笼统说"DDS 慢"。

### Q15 ROS 2 有几种 Executor？区别在哪？

常用三种。

`SingleThreadedExecutor` 单线程，所有回调串行执行，实现简单，行为最容易预测。

`MultiThreadedExecutor` 多线程，共享一个等待集，多个线程竞争取任务。它提供并发能力，但并发度受回调组约束，不是线程数越多越快。

`StaticSingleThreadedExecutor` 在启动时一次性收集所有实体，运行期不再动态添加，省掉了每轮遍历和加锁的开销，适合节点结构固定的高频场景，代价是不能在运行中创建新的发布订阅。

选择依据是负载形态：回调都很短且互不阻塞，单线程足够；存在阻塞型回调（IO、等待），才需要多线程；实体固定且延迟敏感，考虑静态版本。

### Q16 回调组是怎么工作的？MutuallyExclusive 和 Reentrant 有什么区别？

回调组是控制回调并发粒度的机制，每个 callback group 绑定一种互斥策略。

`MutuallyExclusive`（默认）保证组内同一时刻只有一个回调在执行，即使 executor 有多个线程。`Reentrant` 允许组内回调并发执行，同一个回调也可能被多个线程同时进入，因此需要自己保证线程安全。

组与组之间没有互斥关系，不同组的回调可以并发，前提是 executor 有足够的线程。

最常见的错误是把所有回调都留在默认组里——这时候即使配了 `MultiThreadedExecutor`，实际行为仍然接近单线程，而且这种问题在日志里看不出来，只能通过观察线程编号或打点发现。

### Q17 为什么配了 MultiThreadedExecutor，回调还是串行执行？

三个原因，按出现频率排。

第一，默认回调组是 `MutuallyExclusive`，所有回调挤在同一个组里，天然互斥。这是绝大多数"配了多线程却不并发"的根因。

第二，回调本身很短，执行时间远小于调度开销，看不出并发效果；这类场景多线程没有收益，反而增加切换成本。

第三，executor 取任务时需要访问内部结构，存在锁竞争；实体数量很多时，取任务的争用会成为新的瓶颈，表现为线程很多但 CPU 利用率上不去。

验证方法很简单：在回调里打印 `std::this_thread::get_id()`，连续采样看是否出现多个线程号。

### Q18 Executor 的调度开销体现在哪里？

一轮循环是：调用 `rmw_wait` 阻塞等待 → 返回后收集就绪实体 → 逐个取出并执行 → 回到等待。

开销有三块。等待与唤醒本身有延迟，涉及 futex 或 epoll 的唤醒路径，量级几微秒到几十微秒。每轮要遍历实体集合判断谁就绪，实体多时是线性开销。执行前要获取内部锁，多线程下存在争用。

对高频小消息，这几项之和可能超过回调本身的执行时间。这时真正的优化方向不是"把回调写得更快"，而是减少唤醒次数（批量处理）、减少实体数量、或者用静态 executor 省掉遍历。

### Q19 DDS 的接收线程和 Executor 是什么关系？

是上下游关系，不是同一个线程。

DDS 内部有自己的线程：接收线程负责从 socket 或共享内存收包、解析 RTPS、重组样本、放入 reader 的 HistoryCache；事件线程负责发现、心跳、重传等协议行为。样本入队后，才通过 wait set 通知上层。

executor 线程在 `rmw_wait` 返回后，调用 `rmw_take` 把样本从 HistoryCache 取到用户缓冲区，然后执行回调。

这个分工决定了两件事：一是接收线程的优先级通常应高于 executor 线程，否则收包不及时会丢数据；二是如果回调很慢导致 HistoryCache 积压，问题出在 executor 侧而不是网络侧，调 QoS 或加带宽都没用。

### Q20 ROS 2 的 QoS 是怎么映射到 DDS 的？

在 rmw 层做一次结构体转换：`rclcpp::QoS` 先规范化为 `rmw_qos_profile_t`，再由具体实现转换成 DDS 的 QoS 策略。

能映射的主要是五项：Reliability（RELIABLE / BEST_EFFORT）、Durability（VOLATILE / TRANSIENT_LOCAL）、History（KEEP_LAST 带深度 / KEEP_ALL）、Deadline、Lifespan，加上 Liveliness 的粗粒度设置。

不能映射的也不少：TransportPriority、ResourceLimits（缓冲区上限、样本数上限）、Ownership（独占与共享）、DestinationOrder，这些在 DDS 里有完整语义，但 ROS 2 的接口没有暴露，需要下沉到 DDS 配置或代码里改。

这个边界要记牢：面试里如果被问"ROS 2 能不能配 DDS 的资源上限"，正确答案是不能通过 ROS 2 接口配，得改 DDS 层配置。

### Q21 什么是 QoS 不兼容？什么情况下收发双方配不上？

QoS 在发现阶段会做兼容性检查，不兼容的两个端点不会建立通信，表现为 topic 能发现、`ros2 topic info` 能看到双方，但收不到任何数据。

两条基本规则：订阅方的要求不能高于发布方的承诺。RELIABLE 发布配 BEST_EFFORT 订阅是兼容的（订阅方主动降级）；BEST_EFFORT 发布配 RELIABLE 订阅不兼容。TRANSIENT_LOCAL 订阅配 VOLATILE 发布不兼容，因为订阅方要求历史数据，而发布方不提供。

排查手段是 `ros2 topic info --verbose`，它会把双方的 QoS 逐项列出来对比，比读代码快得多。

还有一类隐性不兼容：深度和资源限制不匹配导致的行为差异——不是配不上，而是高负载时静默丢弃，这类问题只能通过计数指标发现。

### Q22 ROS 2 的 allocator 该怎么用？什么情况下值得用？

rclcpp 在创建 publisher、subscription、executor 时支持传入自定义 allocator，消息也可以用 `allocate_shared` 分配，目的都是把内存分配从默认堆转移到预先分配的内存池。

但收益有前提：这条链路上每一层都必须用同一套内存策略。应用层用了池，rmw 层和 DDS 层仍然走默认分配器的话，中间那几次分配和拷贝依旧存在，整体延迟改善有限。

现实中的限制是：DDS 实现的内部缓冲（HistoryCache、序列化缓冲）通常不受 rclcpp allocator 控制，需要单独在 DDS 配置里调（比如 Fast DDS 的 mem policy、iceoryx 的 mempool）。

所以判断标准是：能不能把整条链路的内存来源统一。能，收益明显；不能，不如把精力放在减少拷贝次数上。

### Q23 LifecycleNode 解决什么问题？

它把节点的生命周期显式化成状态机：Unconfigured → Inactive → Active → Finalized，每个转换对应可重写的回调（on_configure、on_activate、on_deactivate、on_cleanup）。

解决的问题有三类。一是启动顺序确定性：依赖外部服务的节点可以停在 Inactive，等条件满足再激活，避免带着错误状态启动。二是热切换与故障恢复：deactivate 可以让节点停止收发但不销毁资源，恢复时不必重建发现关系。三是资源可控：publisher 和 subscription 在 configure 阶段创建、activate 阶段才真正参与通信，可以控制发现流量出现的时间点。

对上电时序敏感的系统（多传感器、多控制器协同启动），这个机制比在 `main` 里靠 sleep 排队可靠得多。

### Q24 什么是 intra-process communication？什么时候有效？

同一进程内的发布者和订阅者可以绕过 DDS 的序列化和传输，直接传递消息对象。启用后，`publish` 传的是指针，订阅方拿到的是同一个对象，省掉了序列化、反序列化、以及跨线程的缓冲区拷贝。

有效的条件有三个：发布和订阅在同一进程、同一 context；节点开启了 intra-process 选项；发布时传的是 `unique_ptr` 而不是 `const 引用`（后者会触发一次拷贝）。

收益在单进程多节点的高频场景里非常明显，比如感知和融合同进程运行。代价是失去了 DDS 的部分语义——QoS 中的 Durability、Deadline 等不再完全生效，消息也不再出现在网络抓包里，调试时容易误判成"没发出去"。

它是默认关闭的，需要显式开启，这个默认值经常让人误以为"同进程也走网络"。

### Q25 怎么诊断 ROS 2 的延迟问题？

先分段，再下工具。

粗测用 `ros2 topic delay`（需要消息带 header 时间戳），能看到端到端延迟的分布；`ros2 topic hz` 和 `ros2 topic bw` 确认频率和带宽是否达到预期。这三条命令能快速判断问题是"没发出来"、"发慢了"还是"收到了但处理慢"。

要定位到具体环节，用 `ros2_tracing`（基于 LTTng）：它提供 rclcpp_publish、rmw_publish、dds_write、callback_start 等 tracepoint，可以直接算出序列化耗时、传输耗时、executor 排队时间各占多少。

再往下是系统层：`perf` 看线程 CPU 分布，`ftrace` 的 sched_switch 看是否被抢占，`perf sched latency` 看调度延迟。

关键是先建立分段模型（发送侧 → 传输 → 接收侧 → executor 排队 → 回调执行），再去测每一段，而不是拿到一个总延迟就开始猜。
