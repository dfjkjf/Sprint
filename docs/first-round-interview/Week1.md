# Week 1：对象、并发与内存

本周围绕一条 6MB 的 ROS 2 点云消息展开：从创建到被订阅方回调处理，中间发生了哪些内存分配、数据拷贝、所有权转移和线程同步，每一步的代价是多少。

四天分工：Day 1 对象生命周期与所有权、Day 2 并发与线程模型、Day 3 内存与拷贝成本、Day 4 架构设计与故障排查。

## Day 1｜对象生命周期与所有权

### Q1 一条 6MB 的消息从创建到发送，中间拷贝几次？

不能给一个固定数字，要先确认走哪条路径，因为四条路径的拷贝次数差别很大。

进程内投递（同进程的发布订阅）参数以 `const` 引用传递，payload 拷贝 0 次。跨进程走 DDS，序列化至少一次——这是把结构化消息压成连续字节流，属于全量拷贝；进入传输层后，UDP 还要再拷一次进内核 socket 缓冲区，接收侧再反序列化一次。走共享内存（iceoryx 或 Fast DDS 的 SHM 传输），省掉的是跨进程那一次 payload 搬运，序列化和反序列化依然保留。只有使用 loan API（应用直接向中间件借一块共享内存、在上面构造消息）时，才能省掉「应用堆缓冲区到中间件缓冲区」这一次。

所以回答顺序是：先问是否跨进程、是否用共享内存、消息是 POD 还是非 POD、是否使用 loan，再给数字。性能分析时关注四个量：分配次数、拷贝字节数、序列化耗时、端到端延迟。

### Q2 `std::vector` 对象和它保存的 6MB 数据是什么关系？拷贝构造和移动构造差在哪？

`vector` 对象本身只包含三个指针（起始、末尾、容量尾），6MB 数据在堆上单独分配，析构时由 `vector` 释放。

拷贝构造要做两件事：分配一块新的 6MB 缓冲区，再逐字节复制，时间复杂度 O(n)。移动构造只交接三个指针，O(1)，源对象进入「有效但未指定」状态，不能假设它为空。

这里有个容易被追问的例外：移动构造只有在两个 `vector` 的分配器兼容时才是 O(1)。如果分配器带状态且 `propagate_on_container_move_assignment` 为 `false` 而两者不相等，移动赋值会退化成逐元素移动，仍然是 O(n)。标准分配器场景下不必担心，但被问到「移动一定更快吗」时要能说出这个前提。

另外 `std::move` 本身不产生任何运行时代码，它只是一个到右值引用的类型转换，真正搬数据的是移动构造函数。

### Q3 既然用了 `std::move`，为什么不能说这条链路实现了零拷贝？

因为两者作用在不同层。移动语义解决的是 C++ 对象之间的资源所有权转移，发生在应用层的堆内存之间；零拷贝解决的是 payload 在通信链路中被搬运的次数，涉及序列化、跨进程、内核缓冲区。

即便应用层完美地移动了对象，进入 DDS 后仍然存在：序列化产生一次全量拷贝；UDP 传输要把数据拷入内核 socket 缓冲区；接收端要反序列化还原成对象。共享内存能消除的是「进程 A 的内存到进程 B 的内存」这一次搬运。

判断标准要落在物理地址上：零拷贝成立的条件是收发双方访问同一块物理内存，而不是代码里没有出现 `memcpy`。所以我在面试里会明确区分三件事——对象移动（省应用层的复制）、数据零拷贝（省跨进程的搬运）、共享内存（实现零拷贝的手段之一），三者不能互相证明。

### Q4 消息要进异步发送队列，所有权怎么转移？

常见写法是接口按值接收，内部再移动到队列元素：

```cpp
void Push(std::vector<uint8_t> msg) { queue_.push(std::move(msg)); }
```

调用方 `Push(std::move(data))` 时发生两次移动构造——实参移动到形参、形参移动到队列元素——payload 拷贝 0 次。

但队列必须有界，这不是性能优化而是正确性要求。设生产 100 条/秒、消费 80 条/秒，队列每秒净增长 20 条，单条 6MB 时内存以 120MB/s 的速度增长；容量 10 条的队列约 0.5 秒填满，不设上限则几分钟内被 OOM killer 终止。

队列长度也不能随意放大。按 Little 定律，队列长度等于到达率乘以平均等待时间，容量越大意味着满负荷时的排队延迟越长。所以容量的定法是从业务允许的最大积压时长反推，而不是拍一个整数。

### Q5 队列满了，能不能对所有消息统一采用丢弃策略？

不能，这是业务语义问题而不是技术选择，不同消息类型必须分开处理。

| 消息类型 | 典型策略 |
| --- | --- |
| 高频传感器（点云、图像） | 丢旧保新，保证新鲜度 |
| 控制指令 | 可靠传递，满了阻塞或超时返回错误 |
| 任务事件 | 保序、保完整性，不能丢 |
| 状态通知 | 可合并、可降采样 |

丢一帧点云的代价是这帧数据不新鲜，下一帧很快就到；丢一条控制指令的代价是状态机与真实状态失配，恢复需要重新对齐。

还有两个工程约束：丢弃必须可观测，要统计丢弃计数并告警，静默丢弃最难排查；降采样和限流也是背压手段，不只是丢弃。

### Q6 异步发送怎么保证消息缓冲区的生命周期安全？

核心原则一句话：后台线程对这块内存的最后一次访问结束之前，它不能被释放。

实现上有三种所有权方案。`unique_ptr` 把所有权转移给异步任务，链路上始终只有一个持有者，语义最清晰，开销最小。`shared_ptr` 用于多方确实需要同时持有的场景，代价是引用计数是原子操作，多核高频拷贝同一控制块会产生 cacheline 争用；同时要清楚，引用计数线程安全并不等于对象的并发读写安全。内存池加自定义 deleter 的方式，是在句柄销毁时把内存块归还池中，适合固定尺寸的高频分配。

最容易被忽略的是超时处理。超时只说明在预期时间内没有收到结果，不代表底层已经停止访问这块内存——内核发送队列里可能还有数据在途，DMA 可能仍在读，对端可能刚拿到指针。所以超时只能触发告警或降级，不能作为归还依据。正确顺序是：先发起取消，收到完成通知或取消确认，确认不再访问，才允许回收。

### Q7 如果异步任务长期不完成，会发生什么？

内存池的可用块会被持续占用并逐块耗尽，之后新的消息分配失败。这个失败通常表现为静默丢数据而不是立即崩溃，因此比崩溃更难发现。

容量规划要按「同时存活量」而不是队列容量计算，存活链路包括：生产者正在填充的、队列中积压的、消费者正在处理的、传输层在途的、已借出但未归还的。只按队列长度配置，第三帧就可能分配失败。

运行时要监控三个指标：内存池占用率、队列水位、发送完成率。三者同时单调上涨，才能判定为泄漏而不是正常波动。

处理手段依次是：任务超时检测（用于告警和降级，不作为回收依据）、取消机制、队列容量上限、资源耗尽时返回明确错误码。顺序不能颠倒——先确认底层不再访问，再回收，最后才允许复用。

## Day 2｜并发与线程模型

### Q8 进程和线程有什么区别？为什么通信中间件通常采用多线程？

进程有独立的虚拟地址空间，线程共享进程的地址空间和文件描述符，但各有独立的栈、寄存器和调度实体。创建线程比创建进程便宜一个数量级，切换时也不需要切换页表。

中间件采用多线程是因为链路上有三个天然可并行的阶段：从传输层接收数据（大量时间在等待 IO）、反序列化（CPU 密集）、执行用户回调（业务耗时不确定）。单线程串行执行时，任何一个阶段阻塞都会拖住整条链路。

线程不是越多越好。一次上下文切换要保存和恢复寄存器、切换栈、还可能污染 cache 和 TLB，量级在几微秒。1kHz 控制回路的周期只有 1 毫秒，几次多余的唤醒就是百分之一的开销，而且会体现在抖动上。

### Q9 什么是用户态和内核态？线程切换一定要进内核吗？

系统调用、中断和异常会从用户态陷入内核态；用户态代码不能直接操作硬件和页表。

线程切换必须经过调度器，因此一定在内核态——即使用户态的协程库，其挂起和恢复最终也要依赖 `futex` 之类不参与调度的系统调用。真正的用户态切换只有协作式协程，但一旦协程内部发生阻塞调用，就会退化成线程阻塞。

这个结论的实际意义是：用 `epoll` 加事件循环减少的是线程数量，从而减少切换次数，但不改变「每次切换都要进内核」这个成本本身。

### Q10 线程阻塞和忙等有什么区别？怎么选？

阻塞会让出 CPU 进入睡眠，代价是唤醒延迟和一次上下文切换；忙等持续占用 CPU 自旋，代价是浪费核心，换来确定的响应延迟。

选择依据是比较「预期等待时长」和「两次上下文切换的成本」。临界区只有几十纳秒时，自旋是划算的；等锁可能超过几微秒，就应该睡眠让出核心。现代实现常用自适应策略，先自旋若干次再挂起。

自旋还有一个前提容易被忽略：自旋的线程数必须小于可用核心数，否则自旋线程互相抢占 CPU，总耗时反而比直接阻塞更长。

### Q11 什么是数据竞争？后果有多严重？

按 C++ 内存模型的定义：两个线程访问同一个内存位置、至少有一个是写操作、并且两者之间没有建立 happens-before 关系。三个条件同时满足即为数据竞争。

后果是未定义行为，不是「可能读到旧值」这么温和。编译器有权假设不存在数据竞争，据此做重排和优化，实际表现可能是读到撕裂的值、循环被优化成死循环、或者优化后的代码与源码语义完全不符。这类问题在 x86 上常常测不出来，换到 ARM 上立刻暴露。

最常见的来源：无锁结构里漏用原子操作；原子只保护了指针而没有保护指针指向的内容；读写锁的使用方式与保护范围不匹配。排查工具首选 ThreadSanitizer，它能在运行时检测出竞争对。

### Q12 如何实现一个线程安全的生产者消费者队列？

三个要素：互斥量保护队列本身、条件变量通知状态变化、谓词防止虚假唤醒。

`wait` 必须带谓词，不能写成裸 `wait()`。原因有三：操作系统允许虚假唤醒；被唤醒后锁可能已被其他线程抢走，条件不再成立；生产者可能在唤醒信号发出与实际抢占锁之间又改动了状态。带谓词的 `wait` 内部是一个 `while` 循环，醒来后会重新检查条件。

有界队列还需要第二个条件变量表示「非满」，否则生产者在队列满时要么忙等要么无法被正确唤醒。停止标志也必须进入谓词，否则 `stop` 之后仍在等待的线程永远醒不过来。

### Q13 为什么不能在持锁状态下执行用户回调？

锁保护的范围应该只是共享数据（队列、计数器、回调列表），而用户回调的执行时间完全不可控。

持锁执行回调的后果是整条生产路径被阻塞：所有生产者在入队时都要等这把锁，而锁的持有时间取决于业务回调的耗时，可能从微秒级变成毫秒级。

正确做法是锁内取出数据和回调列表的快照，出锁后再执行。快照这一步不能省，因为回调列表可能被并发增删，直接把引用传出去可能在执行前就失效了。快照的成本是一次 `vector` 拷贝，复杂度是订阅者数量级，通常远低于持锁回调的代价。

另一点：持锁期间不要做内存分配，分配器内部可能有自己的锁，嵌套加锁会放大竞争面积。

### Q14 一个 callback 阻塞了 20ms，会影响哪些线程和任务？

首先影响同一 executor 或线程池中排在它之后的所有任务，串行地各多等约 20ms；如果这些任务本身有周期，还会造成相位漂移，而不只是延迟增加。

如果这个回调与 1kHz 控制回调共享线程，控制周期是 1ms，那么在最坏情况下连续多个控制周期被吞掉，表现为控制抖动和周期性丢失，这种故障在 CPU 使用率上看不出来。

定位方法是对比每个任务的排队时间与执行时间。埋点必须分开统计这两段（发布侧计时如果包含回调耗时，数据就不可用），排队时间长说明线程被占，执行时间长说明任务本身重。

解法是把长任务隔离到独立线程或独立线程池，或者把任务拆小让出执行权，而不是简单增加线程数。

### Q15 死锁的成因是什么？工程上怎么避免？

死锁需要四个条件同时成立：互斥、持有并等待、不可剥夺、循环等待。破坏任意一个条件即可避免。

工程上最实用的手段是固定加锁顺序（为所有锁定义全局层级，只允许按顺序申请）和一次锁多个（`std::scoped_lock` 内部用避免死锁的算法）。此外要避免在持锁期间回调用户代码——这条路径最难排查，因为死锁点和你写的代码不在同一处，锁的获取分散在业务逻辑里。

排查手段是 `gdb` 的 `thread apply all bt` 或 `pstack` 抓取全部线程栈，找出互相等待的锁环；静态检查工具也能在编译期发现一部分加锁顺序违规。

### Q16 mutex、spinlock、atomic、CAS 应该怎么选？

`spinlock` 适合临界区极短且线程数少于核心数的场景；`mutex` 适合可能等待较久的情况，会让出 CPU；两者都是保护一段逻辑。

`atomic` 只保证单个操作的原子性，不能保证多个变量之间的一致性。需要维护一个不变量（比如队列的头尾指针与计数必须一致）时，仍然要用锁。

CAS 是无锁结构的基础，两个已知问题：ABA（值从 A 变到 B 又变回 A，比较时看不出变化，解法是加版本号或用带标记的指针）、活锁（高竞争下反复重试失败，消耗 CPU 却没有进展）。

选择顺序可以固定下来：能用单个原子变量表达的状态就不加锁；需要维护不变量就用 `mutex`；只有当实测确认锁竞争是瓶颈时才考虑无锁结构。

### Q17 C++ 内存序应该怎么理解？

`relaxed` 只保证该操作本身是原子的，不提供任何跨线程的顺序保证；`acquire` 与 `release` 配对使用，建立 happens-before 关系，前者保证后续读写不会被重排到它之前，后者保证之前的读写不会被重排到它之后；`seq_cst` 提供全局单一顺序，最强也最贵。

生产者消费者场景只需要记两条：生产者把数据写完，再 `store(release)` 那个就绪标志；消费者 `load(acquire)` 看到标志后，才能安全读取数据。

用错的方式是全程 `relaxed`：生产者可能先更新标志再写数据，消费者看到标志却读到未初始化内容——这正是无锁队列里最难复现的 bug。

硬件层面也有差异：x86 是强内存模型，`acquire`/`release` 几乎不产生额外指令；ARM 是弱内存模型，同样的代码会插入屏障指令，性能差异明显。拿不准时用默认的 `seq_cst`，正确但会付出全屏障的代价。

### Q18 为什么通信组件需要线程池，而不是每条消息创建一个线程？

创建线程的成本包括几十微秒的系统调用、一块默认 8MB 的虚拟栈空间、以及一个额外的调度实体。消息频率稍高（比如 1kHz）时，光线程创建和销毁就会占满 CPU。

线程池的核心是预先创建固定数量的工作线程、复用它们、并通过有界任务队列缓冲突发流量。

但长短任务混在同一个池里会产生队头阻塞：一个 20ms 的计算任务排在前面，后面 100 微秒的任务即使很快也必须等，它在 4 个 worker 的池里最坏等待时间接近 20ms。对实时性敏感的路径，必须按任务类型分组，或者给关键路径分配专用线程。

用优先级队列缓解时要意识到它引入新的风险：低优先级任务可能长期得不到执行（饥饿），并且与锁结合时会重新出现优先级反转。

### Q19 实现线程池最容易出什么问题？

两类问题：停止流程和析构安全。

停止流程要按顺序做：先置停止标志，再唤醒所有等待线程，最后逐个 `join`。如果先 `join` 后置标志，工作线程可能永远阻塞在条件变量上。

析构时线程还处于 joinable 状态会直接调用 `std::terminate`，这是标准规定的行为。不能用 `detach` 绕过，因为被分离的线程可能访问已经析构的池对象，产生 use-after-free，而且这类问题在测试环境很难稳定复现。

其他常见问题：工作线程内部调用 `stop()` 会导致自我 `join` 而死锁；任务抛出的异常如果逃出工作函数会终止整个进程，必须在 worker 内捕获；`stop()` 需要保证幂等，重复调用不能出问题。

### Q20 任务队列应该用无锁队列吗？

先回答三个前置问题：是否实测确认锁竞争已经成为瓶颈、能否承担 ABA 与安全内存回收（hazard pointer 或 epoch 回收）的复杂度、是否存在更简单的替代方案。

无锁队列的隐性成本经常被低估：高竞争下 CAS 失败重试会消耗大量 CPU；原子操作与内存屏障本身有开销；在 ARM 等弱内存模型平台上收益更小；调试难度远高于加锁版本，出错形式往往是偶发数据损坏。

多数场景下互斥量队列已经足够——无竞争时 `mutex` 的快路径只有约二十纳秒。无锁的收益只在「高竞争且临界区极短」时才会显现，所以它是最后手段而不是默认选择。

更简单的替代方案往往被忽略：缩短临界区、批量提交、按线程分组以减少共享、用每线程本地队列加周期性汇总。

### Q21 Linux 调度器如何决定哪个线程获得 CPU？

默认的 CFS 按虚拟运行时间（vruntime）选择最欠账的线程，`nice` 值影响权重，每差一级大约相差 1.25 倍 CPU 份额。它追求的是公平而不是低延迟。

实时策略 `SCHED_FIFO` 和 `SCHED_RR` 优先级范围 1 到 99，一旦就绪立即抢占 CFS 线程，且不参与公平分配。这带来一个直接风险：一个实时线程写出死循环，会饿死系统上所有普通任务，包括日志线程和看门狗。

`SCHED_DEADLINE` 按带宽分配（需要指定 runtime、deadline、period），超限会被 throttle，比较适合有明确周期的控制任务。

如果对最坏延迟有严格要求，还需要 PREEMPT_RT 补丁，把内核中大部分不可抢占的临界区改为可抢占；否则即使应用层是实时线程，一次内核长临界区依然会造成毫秒级抖动。

### Q22 CPU 绑核有什么好处和风险？

好处是减少线程在核心之间迁移，保住 L1/L2 中的热数据和 TLB 表项，延迟抖动会明显下降；对高频小消息场景，迁移带来的冷启动成本可能比处理本身还大。

风险有三个：绑核后负载无法均衡，一个核满载另一个空闲；绑核会放大伪共享问题，因为原本会迁移走的线程现在固定在同一行 cacheline 上争用；绑核之后线程无法利用其他核心的空闲时间。

实践做法是只把关键线程绑核，用 `isolcpus` 隔离出专用核心以避免普通任务干扰，同时配置中断亲和性——网络接收中断的 CPU 最好与处理线程同核或同 NUMA 节点，否则数据要跨节点搬运。

### Q23 什么是优先级反转？如何处理？

典型场景：低优先级线程持有锁，被中优先级线程抢占，高优先级线程因等待该锁而被间接饿死。等待时长取决于中优先级线程的执行时间，理论上可以无限长。

三种解法：优先级继承（线程等锁时临时把持有者的优先级提升到自己这一级，Linux 通过 `PTHREAD_PRIO_INHERIT` 的 PI futex 支持）、优先级天花板（锁的优先级设为所有可能使用者的最高值）、以及在设计上避免高优先级路径与低优先级路径共享锁。

在通信组件里这个问题的实际形态是：DDS 接收线程与业务回调共享同一个缓冲区池的锁，如果回调中有低优先级的重任务持锁，实时回调会被拖慢。

### Q24 CPU 使用率很低，callback 延迟却很大，怎么定位根因？

首先要明确：CPU 使用率衡量的是「忙不忙」，不是「快不快」，它不能作为延迟的充分指标。

四类常见原因：线程在等锁；线程被调度出去（被更高优先级抢占或时间片用完）；在等 IO 或共享内存握手；单线程 executor 被前面的长回调阻塞。

工具上先看上下文切换次数，`/proc/PID/status` 里的自愿与非自愿切换计数，或者 `perf sched latency` 看每个线程的调度延迟；再做 off-CPU 分析（`bcc` 的 `offcputime`）看线程阻塞在什么地方；如果切换次数很少而延迟很大，重点怀疑等待对端或 IO。

区分方法很实用：CPU 低且切换频繁，通常是等锁或被抢占；CPU 低且切换很少，通常是在等外部事件。

### Q25 一个组件有 10 个线程，怎么判断要不要加？某个线程长期 100% CPU 怎么查？

线程数按「独立阻塞源」计算，而不是按核心数硬套：等 IO、等锁、纯计算各有独立的阻塞特性，各自需要独立线程。计算型线程数约等于核心数，IO 型可以适当放大，但要有上限。

100% CPU 先区分用户态和内核态，看 `top` 的 us 与 sy 两列。用户态高，用 `perf record -g` 采样后生成火焰图找热点函数；内核态高，用 `perf trace` 或 `strace` 统计系统调用分布，常见原因是自旋锁空转、频繁缺页、或者系统调用粒度过细。

进一步要区分「有效计算」和「无效自旋」：看 IPC（每周期指令数），IPC 很低往往意味着在等内存或自旋；结合 `perf stat` 的 cache miss 计数可以确认。

### Q26 如果让你设计一个高频通信组件的线程模型，你会怎么分配线程？落到 ROS 2 上是什么形态？

基本形态是：一条独立接收线程从 DDS 取数据，写入有界队列；一组固定数量的 worker 线程执行回调；实时性最高的控制回调使用专用线程，不与通用任务共享。

接收线程可以就地执行短回调（inline 处理）以减少一次队列传递和唤醒，但前提是回调耗时有上界且已实测，否则会把接收路径拖死。

对应到 ROS 2：`MultiThreadedExecutor` 配合回调组。控制类回调放在 `MutuallyExclusive` 组并分配专用线程，日志、落盘、参数更新这类任务放在另一个可并发的组。要避免的典型错误是把所有回调都塞进同一个 `MutuallyExclusive` 组，那等于退化成单线程执行。

还要注意 DDS 侧本身就有线程：Fast DDS 的接收与事件处理线程数量由 RMW 配置决定，调应用层线程数之前要先确认底层线程模型，否则调优方向会错。

## Day 3｜内存与拷贝成本

### Q27 内存池解决了什么问题？没有解决什么？

解决的是动态内存分配的调用开销、内存碎片和分配延迟抖动。

具体的数量级值得说清：大于 128KB 的分配在 glibc 中走 `mmap` 而不是 `brk`，每次都要向内核申请、触发缺页异常，释放时归还内核，开销在微秒到毫秒量级且不确定；6MB 的消息完全落在这个区间。改用固定大小内存池之后，取用和归还都只是空闲链表的指针操作，纳秒级。

多线程场景下还有一层：分配器内部的锁和 arena 竞争。`glibc` 用多 arena 缓解，但跨线程释放仍可能产生远程释放开销；线程本地缓存的分配器（tcmalloc、jemalloc）正是为此设计。

内存池没有解决的是数据拷贝。从池中取出一块 6MB 缓冲区后，如果仍然要 `memcpy` 两次，那两次搬运的开销一点没少。所以内存池的收益体现在分配侧，零拷贝的收益体现在搬运侧，两者不能互相替代。

### Q28 内存池和对象池有什么区别？

内存池管理的是原始字节块，不涉及对象的构造与析构，取到的是一块 `void*` 或字节指针，需要 `placement new` 才能变成对象。

对象池管理的是已经构造完成的完整对象，取用时直接可用，省掉的是构造和析构的代价，而不只是分配。

通信场景里传的是 POD 大块数据，构造代价可以忽略，用内存池；连接、会话、序列化器这类带资源初始化（打开文件、注册句柄、分配内部缓存）的对象，用对象池才有意义。

对象池有一个容易被忽略的要求：归还时必须重置对象状态，否则下一个使用者会读到脏数据，这类问题往往表现为难以复现的逻辑错误。

### Q29 内存池有哪些常见实现方式？

四种足够覆盖绝大多数场景。

固定大小分块：所有块大小一致，空闲块用链表串起来，取用归还都是 O(1)，没有外部碎片，代价是每种尺寸要独立一个池。通信场景消息尺寸集中，这种最常用。

分级大小（size class）：按 2 的幂分档，比如 4K、64K、1M、4M、8M，兼顾通用性，内部碎片最坏是 2 倍。

slab 或批量预分配：一次向系统申请一大片连续内存，再自己切分，减少系统调用次数，同时提高页的利用率。

线程本地缓存：每个线程持有自己的小块缓存，避免全局锁；跨线程释放时进入远程释放队列延迟处理。这是现代分配器的核心机制，也可以简化后自建。

### Q30 内存池容量耗尽时应该怎么处理？多线程下如何保证安全？

耗尽策略必须先定义再写代码，三种选择：阻塞等待（可能死锁，只适合非实时路径）、返回错误（推荐，调用方可以决定降级）、按语义丢弃（适合传感器数据）。

多线程实现有三条路：用 CAS 维护无锁空闲栈、加锁保护空闲链表、每线程本地池加全局补充。无锁栈要处理 ABA（空闲块的 `next` 指针是典型的 ABA 场景），加版本号或使用带标记的指针可以解决。

比「忘了归还」更危险的是「重复归还」：同一块内存被归还两次后，会同时分配给两个使用者，产生数据竞争且破坏内容，排查难度极高。防御手段是归还时打标记、块头加魔数、在测试环境启 ASan，或者在调试构建中维护一份已归还块集合。

### Q31 内存对齐为什么会影响性能？

CPU 按字或按 cacheline 访问内存。未对齐的访问可能跨越两个 cacheline，需要两次访问；在 ARM 的一些指令上（如 LDRD、部分 SIMD 指令）未对齐会直接触发异常。

结构体成员的排列顺序会影响实际大小：编译器会在成员之间插入填充字节以满足对齐要求。把大类型放在前面、按尺寸降序排列，能减少填充；高频分配的结构体值得顺手排一下。

`alignas(64)` 用于把变量对齐到 cacheline，主要目的是避免伪共享，而不是为了访问速度。

通信链路中的实际影响：序列化缓冲区如果未对齐，接收端用 `reinterpret_cast` 直接解释二进制内容是未定义行为；使用 AVX/AVX512 等 SIMD 指令时，对齐版本比非对齐版本更快，未对齐数据只能走较慢的指令。

### Q32 什么是伪共享（False Sharing）？怎么解决？

两个线程分别写各自的变量，但这两个变量恰好落在同一条 cacheline 上。硬件以 cacheline 为单位维护一致性，一个核心写入会让其他核心上该行失效，于是同一行在两个核心之间来回迁移（cacheline ping-pong），性能可能比单线程还差。

最常见的位置：生产者与消费者的计数放在同一个结构体、多个线程的统计量相邻存放、序列号和状态标志挨在一起。

解法是把热点变量按 cacheline 对齐（`alignas(64)`）或用填充字节隔离；每线程独立的统计量各自占一行；结构体设计时把只读字段和频繁写入字段分开。

检测工具是 `perf c2c`，它能直接报告哪些地址发生了跨核心的 cacheline 争用，比猜测高效得多。

### Q33 什么是 NUMA？它会影响内存池吗？

在多路服务器上，内存物理上分属不同节点，每个节点有自己的内存控制器。CPU 访问本地节点的延迟最低，跨节点访问要走互联，延迟通常增加到 1.3 到 2 倍，带宽也会下降。

内存池必须按节点分配，否则「池化」省下的分配开销会被远端访存吃回来。手段有 `numa_alloc_onnode`、`mbind` 系统调用，或者通过线程绑核间接控制。

Linux 的首次触碰（first touch）策略决定页面归属：谁先写这个页面，它就分配在谁的节点上。这意味着分配线程和执行线程必须绑定在同一节点，否则分配出来的内存在远端。

通信组件里要确认三件事：共享内存段在哪个节点、DDS 接收线程与业务回调线程是否同节点、中断处理在哪个节点。

### Q34 一次 `memcpy` 的成本主要由什么决定？

大小、对齐情况、源和目标是否在 cache 中、是否跨 NUMA 节点、单线程还是多线程。

分区间看，主导因素不同：小拷贝（几百字节以内）主要由函数调用开销和分支预测决定；中等尺寸（在 L1/L2 容量内）受指令吞吐限制，AVX2 每周期可搬 32 字节；大块（超出 LLC 容量）则是纯内存带宽问题。

6MB 已经超出典型 LLC（几 MB 到几十 MB 之间），因此接近带宽瓶颈，耗时随大小近似线性增长。

所以「memcpy 有多快」这个问题没有统一答案，必须先说明数据大小和工作集是否驻留 cache。

### Q35 如何计算 `memcpy` 的吞吐量？怎么判断已经达到内存带宽瓶颈？

吞吐量等于数据量除以耗时。但要注意有效带宽要算读写两侧，所以实际内存流量约为数据量的两倍，比较时要与理论带宽的一半对齐，否则会得出「超过硬件带宽」的错误结论。

判断到达瓶颈的方法有两个：加大数据量后吞吐不再上升；增加拷贝线程后总吞吐不再随线程数增长。

单线程拷贝通常打不满带宽，因为受限于单核的 load/store 单元，一般只有十几 GB/s；多线程并行可以接近硬件上限。

一旦确认到达带宽上限，继续优化拷贝函数本身就没有意义了，唯一的出路是减少拷贝次数——这才是零拷贝真正的价值所在。

### Q36 大消息的 `memcpy` 为什么要关心 cache 影响？

拷贝会把有用数据挤出 LLC，导致后续处理阶段全部 cache miss。这部分开销不计入 `memcpy` 本身的耗时，但会体现在整条链路的延迟上，属于典型的「隐藏成本」。

缓解手段：尽量只搬一次，避免同一块数据在多层之间来回复制；顺序访问优于随机访问，硬件预取器只对顺序有效；对「写完就不再读」的大块数据，可以用非临时存储指令（`movntdq`）绕过 cache，避免污染。

6MB 点云正好是能挤爆 LLC 的量级，所以在这类系统里，减少一次全量拷贝的收益往往远大于微调拷贝函数。

### Q37 Benchmark 应该怎么设计，数据才能站得住？

三件事：固定环境、先预热、报分布。

固定环境包括：锁定 CPU 频率（避免节能降频导致前后不一致）、绑核、关闭无关负载、确认超线程状态。环境不固定时，测出来的差异可能是噪声。

预热是为了让页表、cache、分支预测器和频率都进入稳态。冷启动数据不能与稳态数据混在一起比较。

报分布而不是均值：至少给出 P50、P95、P99、最大值，加上吞吐量、CPU 使用率、内存峰值。实时性结论几乎总是由尾延迟决定，均值好看但 P99 很差，在控制场景里就是不可用。

样本量要够：要统计 P99，至少需要几千次样本，否则尾部分位数本身没有统计意义。

### Q38 为什么 Benchmark 不能只测一次？怎么保证对比公平？

单次测量混杂了冷启动、缺页异常、频率爬坡和调度噪声，结果不可复现，也无法判断差异是否显著。

公平对比要求：使用同一个二进制和同一份数据、同样的绑核与频率设置、交替执行 A 和 B 多轮（消除随时间漂移的环境因素）、改前改后跑相同轮次。

比较时用中位数或多次运行的中位数，并给出离散程度；有条件时做显著性检验，而不是看到 3% 的差异就下结论。

最常见的错误是拿新方案预热后的数据去比旧方案的第一次运行，这样几乎必然「优化成功」。

### Q39 动态分配和预分配内存池的差距有多大？如果只提升 3%，怎么解释？

量级上通常在一到两成，而且收益主要体现在 P99 和最大值上，而不是均值——这正是容易被平均值掩盖的部分。

如果测出来只有 3%，先不要宣布优化成功：先看抖动是否下降（最大值和标准差），如果抖动降了但均值几乎没变，说明收益是真实存在的；如果抖动也没变，说明瓶颈不在分配器上。

如果减少一次 `memcpy` 能带来 40% 的提升，那么结论很明确：瓶颈在数据搬运和内存带宽上，继续优化分配器没有意义。

三条通用原则：均值不能证明实时性；必须报告最差值；必须说明测试条件（消息大小、频率、并发数、核心数），否则数据无法复现。

### Q40 零拷贝的代价是什么？

四个代价。

生命周期管理变复杂：数据不再由单个用户态对象独占，谁释放、何时释放需要跨进程的所有权协议或引用计数，无法完全交给 RAII。

适用范围受限：共享内存只在同一主机内有效，跨机通信仍然要经过协议栈和拷贝。

序列化并未消除：除非消息本身就是 POD 且两端内存布局完全一致，否则序列化与反序列化的 CPU 开销依然存在，零拷贝只是省了搬运。

调试难度上升：数据位于共享内存段中，出现内容损坏时没有常规的堆栈信息和内存检测工具可用，定位成本高。

另外还有一层隐含代价：取消拷贝之后，数据在共享内存中的停留时间变长，池的占用压力上升，容量规划需要重新核算。

### Q41 设计一套面向大消息的内存管理方案，池要做多大？

容量按「同时存活量」计算，而不是按队列长度。存活链路是：生产者正在填充、队列中积压、消费者正在处理、传输层在途、已借出但未归还。

以一个具体场景核算：4MB 点云、10Hz、允许 200ms 积压，则队列深度为 2 条；加上填充中 1 条、处理中 1 条、传输在途 1 到 2 条，实际需要 4 到 6 条，即 16 到 24MB。如果只按队列长度配 2 条，第三帧就会分配失败。

通用算式是：块数 = 峰值并发消息数 × 安全系数，安全系数覆盖抖动和短时突发，通常取 1.5 左右，再按实际水位监控调整。

方案本体由五部分组成：尺寸分档的固定块池、RAII 句柄负责归还、明确的耗尽策略、水位与分配失败计数监控、以及与底层共享内存池配置的容量对齐（iceoryx 的 mempool 同样需要按此核算 chunk 数量与尺寸）。

## Day 4｜架构设计与故障排查

### Q42 让你设计一个异步通信组件，你会先考虑什么？

先确定约束，而不是先画类图。四个必答问题：最大消息尺寸是多少、峰值频率是多少、能接受的最大延迟和抖动是多少、内存预算上限是多少。

这四个数直接决定架构走向。6MB 且 10Hz 的场景受内存带宽约束，重点在减少拷贝；1KB 且 1kHz 的场景受调度和唤醒约束，重点在线程模型和锁竞争。两者用同一套设计会导致在错误的地方优化。

还需要补充四个约束：是否跨机、消息类型是否 POD、可靠性要求（是否允许丢弃）、是否需要多订阅者。

约束不明确就开始写代码，后面几乎必然返工。

### Q43 整体架构怎么分层？

分三层，依赖方向自上而下，上层不感知具体传输实现。

接口层只暴露 Topic、QoS、回调类型，业务代码不需要知道底层是进程内投递、共享内存还是网络传输。传输层负责选路和具体实现：进程内直接调用、同机优先共享内存、跨机走网络协议。资源层管理缓冲区池、队列和线程。

关键在于接口层不能绑定具体传输，否则将来更换协议（DDS 换 Zenoh、或从 UDP 换共享内存）就要改动业务代码。

选路应该由中间件根据拓扑、QoS 和消息特征自动决策，而不是让业务代码硬编码。业务可配置的只有 Topic、QoS、回调线程模型和日志级别；传输选择、内存管理、服务发现、序列化和线程绑核应当由中间件自管。

### Q44 接口应该设计成什么样？

三个核心操作 `Start`、`Publish`、`Stop`，加一个析构函数兜底。

`Publish` 建议按值接收消息，内部移动，返回布尔值表示「是否成功入队」。这个返回值不能省——队列满或组件已停止时必须能通知调用方，否则就是静默丢弃。同时要明确返回值的语义是「已受理」而不是「已发送」，两者相差一整个异步链路的延迟。

`Stop` 需要满足三个性质：幂等（重复调用安全）、可等待（能阻塞直到在途任务结束或超时）、不抛异常（析构路径上不能失败）。

### Q45 如果 worker 正在发送时调用 `Stop()`，应该怎么处理？

不能直接终止线程，也不能立刻回收它正在使用的缓冲区。

正确顺序是：置停止标志、拒绝新消息、唤醒所有等待线程、等待在途任务自然结束或到达超时、确认底层不再访问缓冲区、回收缓冲区、最后 `join` 线程。

核心认识是：关闭语义与在途资源回收是两个独立阶段。把两者混在一起，就会出现「线程已退出但缓冲区仍被 DMA 读取」的 use-after-free。

还要注意不能无条件阻塞 `join` 一个卡在 IO 上的线程，否则 `Stop` 本身会挂死。需要设置超时，超时后走强制取消路径，并记录一条错误日志以便事后分析。

如果使用 loan API，还要区分两种情况：已 `publish` 的借出块所有权已移交中间件，未 `publish` 的必须显式释放，否则就是泄漏。

### Q46 系统运行一段时间后内存持续增长，怎么排查？

第一步是分类，而不是直接上工具。三种情况：真正的泄漏（单调增长且不可回收）、消息积压（随负载下降可消退）、正常缓存（有上限且稳定）。

第二步按层次查。进程内存看 `/proc/PID/status` 的 VmRSS 曲线，配合 `pmap` 看是哪类映射在涨；分配热点用 massif 或 `perf mem`；如果怀疑共享内存，看 `ipcs -m` 的段数量和 `df -h /dev/shm` 的占用。

第三步看消息层：DDS 的 History 队列是否持续积压、writer 借出的 sample 是否未归还、订阅者注销后回调列表是否仍在增长。

最常见的三个根因：回调消费速度跟不上导致 History 持续增长；loan 之后走了失败分支未释放；订阅者未正确注销导致回调对象与计量对象泄漏。判据始终是那三条：是否单调增长、是否可回收、增长是否与业务负载对应。

### Q47 对延迟敏感的系统，应该把所有线程都设成实时调度策略吗？

不应该。全部设为 `SCHED_FIFO` 等于取消了调度器的保护机制。

风险很直接：任何一个实时线程出现死循环，系统上所有普通优先级任务都会饿死，包括日志、看门狗和远程登录，故障现场无法登录排查，只能重启。

正确做法是只把控制回路这一条线程设为实时并绑核，给它明确的优先级和 CPU 时间预算，其余线程保持 CFS。同时用 `RLIMIT_RTPRIO` 或 `CAP_SYS_NICE` 控制谁能提升优先级，避免任意进程抢占系统。

还需要注意两点：实时线程与普通线程共享锁时会出现优先级反转，需要用 PI mutex；在 PREEMPT_RT 内核上中断被线程化，其默认优先级可能低于你的业务线程，需要重新规划优先级顺序，否则中断处理会被延迟。

### Q48 如果必须在吞吐量、延迟和内存占用之间做取舍，你怎么选？

这不是技术选择，而是由业务目标决定优先级。

先确定约束的量级。按 Little 定律，队列长度等于到达率乘以等待时间，因此降低延迟必然要求减少缓冲，而减少缓冲必然增加丢弃概率——这三个指标不是并列关系，而是相互约束。

传感器数据优先新鲜度和尾延迟，宁可丢弃过期帧；控制指令优先不丢失，可以接受排队延迟和更多内存；嵌入式平台优先内存上限，宁可限制队列深度。

所以我的答法是先讲清业务属于哪一类，再说明在该类下哪个指标是硬约束、哪两个可以让步。脱离业务谈「三者兼顾」是不成立的。

### Q49 用三分钟介绍这个组件的设计方案，你怎么说？

按四条线讲。

数据路径：生产者向内存池申请缓冲区，填充完成后把所有权移交组件，后台 worker 负责发送，传输层确认完成后再归还内存池。

并发模型：有界队列加固定数量的 worker，长任务隔离到独立线程，实时性最高的回调使用专用线程，不与通用任务共享。

内存管理：默认独占所有权，只在回调可能跨越对象边界时才升为共享引用；引用计数只保证对象存活，内容并发安全另行保证；超时只触发告警和降级，不作为回收依据。

验证方法：报 P50 到最大值六个指标，说明测试条件，用交替多轮对比消除环境漂移。

最后补一条贯穿性结论：每一次缓冲区借用都必须有确定的、唯一的归还点，且归还时机以底层确认不再访问为准。这是我在处理内存持续增长问题时得到的最实用的一条原则。
